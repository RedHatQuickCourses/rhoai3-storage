Custom Connections & Databases

Data doesn’t just live in buckets. It lives in rows, columns, and vector embeddings.

In the previous modules, we focused heavily on unstructured data (models, logs, pipeline artifacts) stored via S3 or OCI protocols. However, real-world AI—especially Retrieval-Augmented Generation (RAG) and predictive modeling—requires structured data.

If you stop your automation at S3, your data scientists will bypass the platform and go back to hardcoding PostgreSQL passwords directly into their Jupyter Notebooks.

In this module, you will learn how to extend the "AI Factory" by creating Custom Connection Types. You will teach OpenShift AI how to securely speak to any database or external API.

1. The Limitation of Default Types

Out of the box, OpenShift AI 3.3 provides pre-installed Connection Types for:

  • S3-compatible object storage

  • OCI-compliant registries

  • URI-based repositories

It does not provide a default form for Snowflake, MongoDB, MySQL, or Milvus. To support these, the Platform Engineer must define the schema using the ConnectionType custom resource.

2. Architecting a Custom Connection Type

A ConnectionType is a Kubernetes Custom Resource (CR) that tells the OpenShift AI dashboard how to render a form, and critically, how to map the user’s inputs to standard Environment Variables.

Example: Defining a Corporate PostgreSQL Standard

Imagine your organization requires data scientists to query an internal PostgreSQL database. You want to ensure the connection strings are standardized.

As a cluster administrator, you apply the following YAML to your cluster:

apiVersion: dashboard.opendatahub.io/v1alpha
kind: ConnectionType
metadata:
  name: corporate-postgres-v1
  labels:
    opendatahub.io/dashboard: "true"
    opendatahub.io/managed: "true" # <-- REQUIRED FOR 3.3 UI VISIBILITY
spec:
  displayName: "Corporate PostgreSQL"
  description: "Standard connection for read-only transactional databases."
  category: "Database"
  fields:
    - name: Host
      type: text
      required: true
      envVar: DB_HOST
    - name: Port
      type: text
      defaultValue: "5432"
      required: true
      envVar: DB_PORT
    - name: Database
      type: text
      required: true
      envVar: DB_NAME
    - name: Username
      type: text
      required: true
      envVar: DB_USER
    - name: Password
      type: password
      required: true
      envVar: DB_PASSWORD

The Payoff: Code Portability

Once this type is applied, users can create a connection from the dashboard UI. The platform securely injects the credentials into their workbench.

The data scientist writes code that works anywhere, without ever seeing the password:

import os
import psycopg2

# The Platform injects the correct values based on the environment.
conn = psycopg2.connect(
    host=os.getenv("DB_HOST"),
    database=os.getenv("DB_NAME"),
    user=os.getenv("DB_USER"),
    password=os.getenv("DB_PASSWORD")
)

3. The 3.3 Database Mandates (Required Connections)

In OpenShift AI 3.3, setting up database connections is no longer just for custom data science workloads; it is a strict requirement for the platform’s control plane.

You will need to architect connections to the following external systems to support production AI:

A. The Model Registry (Metadata)

  • Requirement: External MySQL (version 5.x or 8.x) or MariaDB (version 10.3+).

  • Why: Local SQLite files are deprecated for production metadata. The Model Registry interacts directly with the underlying relational database to track lineage, quantization schemas, and pipeline deployment events without database locking issues.

B. Llama Stack (Retrieval-Augmented Generation)

When deploying GenAI models that require RAG architectures (giving LLMs access to your private documents), you must connect to specialized vector databases.

  • Vector Store (Large Scale): Requires a connection to Remote Milvus. This typically utilizes a gRPC endpoint on port 19530.

  • Vector Store (Transactional): Requires a connection to PostgreSQL with the pgvector extension, typically on port 5432.

  • State/Metadata: Llama Stack requires PostgreSQL to persist critical GenAI state data, including agent states and conversation history.

Certificate Verification for Databases

If your external databases (like Amazon RDS or an internal Postgres instance) use self-signed certificates, the AI pipelines manager and Model Registry will fail to connect.

You must inject your custom Certificate Authority (CA) bundle into the DSCI (Data Science Cluster Initialization) resource, or the connections will result in an x509: certificate signed by unknown authority error.
